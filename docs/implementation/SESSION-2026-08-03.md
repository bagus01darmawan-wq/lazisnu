### 1.3 Hardening `scripts/backup.sh`

Perubahan utama (semua teruji end-to-end):

- Preflight: env file readable, variabel wajib ada, command tersedia, **free space minimal 1024 MB**, `pg_dump` executable.
- Lock internal `flock` (fd 9) agar tidak bertumpuk; skip jika ada backup lain.
- `timeout --foreground 15m` pada `pg_dump`.
- Dump ditulis ke `*.sql.gz.part` dulu; `gzip -t` + non-empty baru di-`mv`.
- Upload R2, lalu **verifikasi ukuran via `head-object`** (bukan hanya exit code `aws s3 cp`).
- Marker sukses `backup-status/lazisnu-latest.json` (status, key, timestamp epoch, size, sha256) diupload + diverifikasi.
- Log eksplisit: `SUCCESS backup=... r2_key=...` atau `FAILURE stage=... reason=... exit_code=...` (via trap EXIT).
- Cleanup: placeholder <1KB, retention 90 hari + archive ke R2 prefix `archive/` sebelum hapus lokal.
- Output console dibuat immune terhadap SIGPIPE (kasus koneksi SSH terputus).

Contoh log sukses:

```
[2026-08-03 11:04:38] SUCCESS backup=/opt/lazisnu/backups/lazisnu_20260803_110434.sql.gz r2_key=backups/lazisnu_20260803_110434.sql.gz size_bytes=81530
```

### 1.4 `scripts/backup-healthcheck.sh` + Cron

- Berjalan independen tiap jam menit 17 via `/etc/cron.d/lazisnu-backup-health` (`flock` + `timeout 5m`).
- Membaca marker R2, memvalidasi: status success, key format `backups/*.sql.gz`, ukuran object cocok, usia `completed_at_epoch` <= 26 jam (fallback LastModified marker).
- Alert opsional via `BACKUP_ALERT_WEBHOOK_URL` (Discord), dedup via state file `.backup-health-alert`, log ke `backup-health.log` + `logger` (journald).
- Uji: `BACKUP_MAX_AGE_HOURS=0` menghasilkan FAILURE + `ALERT_NOT_SENT` (webhook belum di-set saat uji pertama); kondisi normal kembali SUCCESS. Webhook kemudian diisi user (`BACKUP_ALERT_WEBHOOK_URL='https://discord.com/...'` di `secrets/env.backup-2026-07-27`) dan terverifikasi ada di file.

### 1.5 Cron Root & Flag Path

- Root crontab di-update: backup harian memakai `flock -n /run/lock/lazisnu-backup.lock` + `timeout 15m`; certbot memakai script baru (lihat bagian 2.4).
- **Insiden internal:** percobaan update crontab via pipeline `sed | crontab -` gagal karena quoting PowerShell/SSH dan sempat mengosongkan crontab root. Dipulihkan segera dari `scripts/lazisnu-root-crontab` (4 job: stargate, certbot, backup DB, backup kuma) dan diverifikasi.
- Flag path konsisten di runtime: `/opt/lazisnu/backup-data/active` (script + compose `BACKUP_FLAG_PATH`); `backup-active` legacy masih ada tapi tidak dipakai. SOP diperbarui.
- **CRLF:** `deploy-blue-green.sh` ter-copy dengan CRLF menyebabkan `syntax error near $'{\r'`; dinormalisasi ke LF (`.gitattributes *.sh text eol=lf` + normalisasi manual), `.gitattributes` ditambah `*.conf.example text eol=lf`.

## 2. Insiden "Server Down" 02:00 Jakarta — Cron Certbot Standalone

### 2.1 Gejala

Alert Uptime Kuma/Discord pukul 02:00 (Asia/Jakarta): `dashboard.lazisnu.site`, `staging.lazisnu.site`, `staging-api.lazisnu.site` — `connect ECONNREFUSED :443`. VM tidak reboot (up 10 hari), backup DB bukan penyebab.

### 2.2 Akar Masalah

- Timezone: VM `Asia/Shanghai` (UTC+8), Discord `Asia/Jakarta` (UTC+7). Alert 02:00 Jakarta = **03:00 VM**.
- Cron lama pukul 03:00 Senin: `docker compose stop nginx && docker run ... certbot renew --standalone && docker compose up -d nginx`.
- Nginx gagal start: `host not found in upstream "blue-backend:3001"` — `nginx/upstream.conf` masih menunjuk `blue-backend` yang sudah tidak ada (state blue-green tidak sinkron).
- Nginx restart loop (exit 1, restart count 236+), port 80/443 mati.
- `docker compose up -d nginx` juga membuat container `lazisnu-backend-1`/`lazisnu-web-1` baru (depends_on), tapi upstream tetap salah.
- Error cron tidak terlihat: `No MTA installed, discarding output`.

### 2.3 Pemulihan

- Verifikasi green sehat: `green-backend:3101 /health/ready = 200`, `green-web = 307`.
- `upstream.conf` diarahkan ke `green-backend:3101` / `green-web:3100`, nginx direstart, `nginx -t` OK.
- Endpoint pulih: dashboard 307, staging 307, staging API 200.

### 2.4 Perbaikan Permanen

- `scripts/certbot-renew-safe.sh`: renewal **webroot** tanpa stop nginx; preflight nginx running; `flock` + `timeout 10m`; setelah renew → `nginx -t` → `nginx -s reload`; log `/var/log/lazisnu-certbot-renew.log` + journald.
- Cron root: `0 3 * * 1 /usr/bin/flock ... /usr/bin/timeout --foreground 15m /opt/lazisnu/scripts/certbot-renew-safe.sh`.
- Uji manual: SUCCESS tanpa downtime, endpoint tetap sehat.

## 3. Insiden 502 Production API — Stale Static Upstream Setelah Recreate

### 3.1 Gejala

Setelah rotasi password (recreate `green-backend` 11:04): web production Overview "coba lagi", WA Monitor "network error", Master "gagal mengambil data ranting", Android login "tidak ada koneksi internet". Staging API tetap 200.

### 3.2 Akar Masalah

- `https://api.lazisnu.site/v1/health/ready` dan `https://dashboard.lazisnu.site/v1/...` → **502**, sedangkan `127.0.0.1:3101/health/ready` → 200.
- nginx memakai **static upstream** (`upstream backend_active { server green-backend:3101; }`) yang di-resolve **sekali saat start** (nginx start 07:47, green direcreate 11:04 → IP berubah 172.18.0.15) → koneksi ke IP lama mati.
- Staging tidak terdampak karena memakai `proxy_pass $variable` + `resolver` (resolve per-request).
- Login web yang berhasil terjadi sebelum recreate; setelahnya semua fetch data gagal.

### 3.3 Pemulihan & Perbaikan Permanen

- Segera: `nginx -s reload` → API pulih 200.
- Permanen: upstream production diubah ke pola dynamic seperti staging:

```nginx
# nginx/upstream.conf (dikelola deploy-blue-green.sh)
set $backend_upstream "http://green-backend:3101";
set $web_upstream "http://green-web:3100";
```

- `nginx.conf`: `proxy_pass http://$backend_upstream` / `http://$web_upstream` (resolver 127.0.0.11 sudah ada).
- `scripts/deploy-blue-green.sh` `update_nginx_upstream()` menulis format `set` (escaped `\$` di heredoc); `get_active_color()` tetap kompatibel (grep nama container).
- `nginx/upstream.conf.example` diperbarui. `nginx -t` + reload lulus; endpoint production/staging/status sehat.
