## 3. Penjelasan Detail `/var/cache/apt` dan `/var/lib/snapd/cache`

### 3.1 `/var/cache/apt` (230M)

- **Isi**: file `.deb` (paket installer) yang diunduh saat `apt install/upgrade`
- **Mengapa tumbuh**: apt men-download `.deb` ke cache dulu sebelum ekstrak-install; tidak menghapus setelah sukses. Sebelum Ubuntu 22.04 ada auto-clean (`APT::Periodic::AutocleanInterval`), di 22.04+ default dimatikan
- **Mengapa perlu hapus berkala**: 99% tidak dipakai ulang, versi kedaluwarsa menumpuk, yang aktif sudah ter-ekstrak di `/usr/lib` `/usr/bin` dll, bandwidth murah
- **Cara bersihkan**: `sudo apt-get clean` (hapus semua) atau `apt-get autoclean` (yang versi lama saja)
- **Risiko**: nihil — tidak ada aplikasi yang membaca `/var/cache/apt/archives` saat runtime

### 3.2 `/var/lib/snapd/cache` (509M)

- **Isi**: file `.snap` (paket snap) yang sudah diunduh. Snapd dipakai untuk Docker, certbot, beberapa tool sistem
- **Mengapa tumbuh**: setiap `snap refresh` (2× sehari otomatis via `snapd.refresh.timer`) mendownload `.snap` baru dan tidak pernah menghapus versi lama dari cache. Tidak ada internal cleanup sama sekali
- **Mengapa perlu hapus berkala**: versi lama tidak terpakai (aktif hanya revisi terbaru `snap list --all`), yang dipakai sudah di-mount dari `/var/lib/snapd/snaps/` BUKAN dari cache, cache tidak dipakai untuk rollback, tumbuh >500M dalam 3-6 bulan
- **Cara bersihkan**: `sudo rm -rf /var/lib/snapd/cache/*` (touch hanya cache, tidak menyentuh `/var/lib/snapd/snaps/` atau `assertions/`)
- **Risiko**: nihil — refresh berikutnya download ulang jika perlu

### 3.3 Perbandingan Ringkas

| Aspek | `/var/cache/apt` | `/var/lib/snapd/cache` |
|---|---|---|
| Format | `.deb` | `.snap` |
| Auto-clean default | Tidak (Ubuntu 22.04+) | Tidak |
| Frekuensi refresh | Tidak teratur (saat patch security) | Automatic 2× sehari |
| Cache dipakai utk rollback? | Tidak | Tidak |
| Risiko hapus | Aman | Aman |

**Kesimpulan**: `/var/lib/snapd/cache` sebenarnya lebih agresif tumbuh daripada `/var/cache/apt` karena snapd refresh otomatis 2× sehari.

## 4. Pemasangan Cron Mingguan Housekeeping

### 4.1 Keputusan User

User setuju cron mingguan untuk 3 sumber growth tanpa batas:
1. `/var/cache/apt` → `apt-get clean`
2. `/var/lib/snapd/cache` → `rm -rf`
3. `/var/log/journal` → `journalctl --vacuum-time=7d`

File lain (grafana-data, .git, snapd/seed, containerd aktif) **ditinggalkan** sesuai instruksi user.

### 4.2 File Script Baru

**`scripts/vm-cleanup-weekly.sh`** (di repo, commit TBD):

```bash
#!/bin/bash
# Housekeeping Mingguan — apt cache + snapd cache + journal vacuum 7d
# Aman: tidak menyentuh image container, snap aktif, metrik, atau data aplikasi
# Log: /var/log/lazisnu-cleanup.log

set -euo pipefail
LOG=/var/log/lazisnu-cleanup.log
BEFORE=$(df --output=avail -BM / | tail -1 | tr -d ' M')

{
  echo "[$(date -Iseconds)] Lazisnu weekly cleanup START — free before: ${BEFORE}M"
  apt-get clean
  rm -rf /var/lib/snapd/cache/*
  journalctl --vacuum-time=7d
  AFTER=$(df --output=avail -BM / | tail -1 | tr -d ' M')
  echo "[$(date -Iseconds)] END — free after: ${AFTER}M (delta: $((AFTER - BEFORE))M)"
} >> "$LOG" 2>&1
```

### 4.3 Pemasangan di VM

```bash
scp scripts/vm-cleanup-weekly.sh lazisnu:/tmp/lazisnu-cleanup
ssh lazisnu "sudo install -m 0755 -o root -g root /tmp/lazisnu-cleanup /etc/cron.weekly/lazisnu-cleanup && rm /tmp/lazisnu-cleanup"
```

Verifikasi:
- `-rwxr-xr-x 1 root root 1845 Aug 2 04:12 /etc/cron.weekly/lazisnu-cleanup` ✅

## 5. Analisis Journal Noise — Temuan Insiden 1 Agustus

Saat user mempertimbangkan ulang apakah 7 hari tepat, saya menyelidiki pemicu pertumbuhan journal.

### 5.1 Konfigurasi journald

- `/etc/systemd/journald.conf`: hanya header `[Journal]`, **semua directive berkomentar** → pakai default tanpa limit
- Tidak ada drop-in override di `/etc/systemd/journald.conf.d/`
- 1 boot saja: `Sun 2026-07-26 13:07:12 CST — Sun 2026-08-02 04:16:00 CST` (7 hari)
- `journalctl --disk-usage`: 805.5M → growth rate ~115M/hari

### 5.3 Sample Entry — Akar Masalah Teridentifikasi

```
Aug 01 09:30:01 VM-0-6-ubuntu rsyslogd[797]: file '/var/log/auth.log'[8] write error — No space left on device
Aug 01 09:30:01 VM-0-6-ubuntu rsyslogd[797]: action 'action-2-builtin:omfile' message lost
Aug 01 09:30:01 VM-0-6-ubuntu rsyslogd[797]: 495 messages lost due to rate-limiting (500 allowed within 5 seconds)
```

### 5.4 Mekanisme Feedback Loop (Insiden 1 Agustus)

Ini bukan pertumbuhan natural journal — **artefak insiden disk penuh**:

1. Saat disk capai 100% (1 Agustus, saat deploy-staging gagal karena `git fetch` No space left), rsyslog tidak bisa menulis ke `/var/log/auth.log` dan `/var/log/syslog`
2. rsyslog melaporkan error "No space left on device" → dikirim ke journald
3. journald menyimpan error itu di `/var/log/journal/...`
4. Setiap 5 detik, **495 messages di-rate-limit** = puluhan ribu entry duplikat terkunci dalam journal hanya dalam beberapa menit
5. Journal file ter-rotate setiap ~5 menit saat entry rate meledak (8M/file)

### 5.5 Distribusi File Journal (via `journalctl --header`)

- Hampir semua file ber-timestamp **Sat 2026-08-01 05:31 → 12:33** (±7 jam saat insiden)
- Setiap file 8M, entry count ~5588 (terkunci rate-limit)
- File paling baru (Aug 02 02:06) justru kecil (3669 entries) = kondisi normal kembali
- Journal setelah Aug 01 12:34 sepi → konfirmasi noise terkonsentrasi saat insiden

### 5.6 Diskusi Opsi Vacuum + Keputusan User

Saya sajikan opsi:

| Opsi | Retensi | Yang Tersisa |
|---|---|---|
| `--vacuum-time=3d` | 3 hari | Log pasca-recovery (noise Aug 1 hilang) |
| `--vacuum-time=7d` ⭐ | 7 hari | Termasuk seluruh noise Aug 1 |
| `--vacuum-time=14d` | 14 hari | Sama dengan 7 hari (VM baru 7 hari) |
| `--vacuum-size=200M` | Berbasis ukuran | Auto-trim terbaru, plasma proteksi |
| **Kombinasi `time=7d` + `size=500M`** | Hybrid | Retensi 7 hari + cap insiden |

Saya merekomendasikan kombinasi `time=7d` + `size=500M` karena tahu journal bisa membengkak saat insiden. Namun **user memilih hanya `--vacuum-time=7d`** — keputusan dihormati, cron mingguan tidak diubah.

### 11.3 Interpretasi

- `walg_enabled: true` awal saya sangka = backup aktif. **Menyesatkan**. WAL-G adalah engine yang dipakai Supabase untuk backup, tapi di free plan WAL-G tidak dijadwalkan. WAL-G aktif jika user upgrade ke Pro.
- `pitr_enabled: false` konsisten — PITR (Point-in-Time Recovery) fitur Pro.
- Supabase free plan: **tidak ada backup native**, harapan "daily backup" yang ditulis di banyak dok umum sebenarnya hanya berlaku Pro plan.
- Backup history juga tidak diekspos via API di free tier (`backups: []`), konsisten dengan catatan D5 di TASK-PENDING.
