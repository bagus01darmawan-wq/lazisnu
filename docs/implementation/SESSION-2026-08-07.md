## 8. Temuan: Prometheus Scrape Target Mati saat Blue Aktif (Gap Sinkronisasi Blue-Green)

**Gejala** (saat audit ulang VM untuk `docs/VM-STRUCTURE.md`): target `lazisnu-backend` di Prometheus **DOWN** — `dial tcp: lookup green-backend: no such host`.

**Akar masalah (2 lapis):**
1. **Konfigurasi hardcode satu warna**: `prometheus/prometheus.yml` hanya menarget `green-backend:3101` (keputusan Sesi 03, commit `2df92ef` — target `backend:3001` dihapus karena container base tidak ada). Port `3101` = `BACKEND_PORT_GREEN` (deploy-blue-green.sh), port blue = `3001`.
2. **Tidak ada sinkronisasi saat switch warna**: `deploy-blue-green.sh` menulis ulang `nginx/upstream.conf` (via `update_nginx_upstream()`), tapi **tidak pernah menyentuh `prometheus.yml`**. Sejak deploy v1.0.2 (2026-08-04, `upstream.conf` → "Active: blue"), warna aktif = **BLUE**, container green di-teardown (`AUTO_TEARDOWN=1`) → `green-backend` tidak ada di DNS Docker → scrape mati → monitoring backend kosong (alert `BackendDown` rawan false-firing).

**Mengapa tidak terdeteksi lebih awal**: dokumentasi mencatat perubahan `prometheus.yml` hanya sampai Sesi 03 ("target bersih"), tidak ada sesi yang mengidentifikasi bahwa Prometheus harus mengikuti warna aktif. `DEPLOYMENT.md` menggambarkan `green-backend:3101` sebagai IDLE (benar), tapi tidak ada catatan bahwa scrape target harus selalu ada di kedua warna.

**Perbaikan (Opsi A — perubahan minimal, PR #40?):**
```yaml
- job_name: "lazisnu-backend"
  metrics_path: /metrics
  static_configs:
    - targets: ["blue-backend:3001", "green-backend:3101"]
```
- Kedua target selalu dipasang → warna yang aktif selalu ter-scrape; warna idle akan down (normal, non-fatal) dan up kembali saat di-switch.
- Tidak menyentuh script deploy (tidak perlu restart/reload Prometheus per deploy).
- File: `prometheus/prometheus.yml` (+ catatan komentar alasan).

**Catatan rollout**: prometheus container di VM di-manage compose `docker-compose.yml`; perbaikan via PR (merge → CI build-image → deploy) hanya menyalin source, **container Prometheus perlu `docker compose up -d`/restart + verifikasi target** setelah file sampai ke VM.

> ⚠️ **Pelajaran rollout (2026-08-08)**: `docker compose up -d --force-recreate prometheus` **gagal** karena compose mencoba rebuild image `lazisnu-backend` (build context menyentuh `grafana-data/` yang tidak bisa dibaca) → gunakan **`docker restart lazisnu-prometheus-1`**. SIGHUP reload **tidak cukup** setelah `git checkout -f`: git mengganti file dengan inode baru, bind mount container masih menunjuk inode lama (ter-unlink) → isi `/etc/prometheus/prometheus.yml` di container tetap versi lama. `docker restart` re-mount path ke inode baru → config baru termuat. Verifikasi pasca-restart: `blue-backend:3001` up, `green-backend:3101` down (normal), 33 series `http_requests_total` ter-scrape.

### 8.2 Upgrade Uptime Kuma :1 → :2 (2026-08-08) — Insiden Migrasi + Solusi

**Latar**: Kuma 1.23.17 tidak mengirim notif UP setelah staging API pulih (05:15 WIB) — bug [louislam/uptime-kuma#6046](https://github.com/louislam/uptime-kuma/issues/6046) (notif hilang tanpa retry). Webhook terverifikasi sehat (204). Pilihan user: **Opsi B — upgrade permanen ke `louislam/uptime-kuma:2`** (PR #46).

**Insiden saat deploy v2.5.0**: container crash-loop `Failed to prepare your database: Aggregate table migration is already in progress`.

**Akar masalah (2 lapis)**:
1. Migrasi agregat v2 (`stat_*`) gagal dengan `SQLITE_CONSTRAINT: FOREIGN KEY constraint failed` — DB berisi **5794 heartbeat orphan** + 3 `monitor_tls_info` untuk monitor id 1–5 yang sudah dihapus (setup ulang Kuma ke id 10–13, Sesi 31). Migrasi agregat mencoba insert stat untuk monitor yang tak ada → FK error → state `migrateAggregateTableState="migrating"` macet → crash-loop.
2. Kneks migration v2 sudah jalan (52 migrasi tercatat) tapi state agregat tidak pernah selesai.

**Solusi (3 langkah)**:
```bash
# 1. Backup DB yang gagal (untuk forensik)
cp /opt/lazisnu/uptime-kuma/data/kuma.db backups/kuma-preupgrade/kuma-migrated-failed.db

# 2. Restore DB v1 asli (backup pre-upgrade) + hapus orphan FK
cp backups/kuma-preupgrade/kuma-online.db /opt/lazisnu/uptime-kuma/data/kuma.db
sqlite3 kuma.db "PRAGMA foreign_keys=ON;
  DELETE FROM heartbeat WHERE monitor_id NOT IN (SELECT id FROM monitor);
  DELETE FROM monitor_tls_info WHERE monitor_id NOT IN (SELECT id FROM monitor);"
# Verifikasi: PRAGMA foreign_key_check → 0 baris

# 3. Start ulang v2
docker compose -f docker-compose.yml up -d --no-deps uptime-kuma
```

**Verifikasi pasca-fix (PASS)**: v2.5.0 `Up (healthy)`, status page `status.lazisnu.site` 200 (follow redirect), 4 monitor UP (heartbeat baru), binding `monitor_notification` 1–4 intact, FK check 0.

**Pelajaran**: upgrade major Kuma 1.x → 2.x mensyaratkan DB **bebas orphan FK** — monitor yang dihapus tetap meninggalkan data `heartbeat`/`monitor_tls_info`. Selalu `PRAGMA foreign_key_check` sebelum upgrade. Backup DB wajib (sudah ada `backup-kuma.sh` + backup manual pre-upgrade di `backups/kuma-preupgrade/`).
