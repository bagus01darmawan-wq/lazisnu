## 2. Fix Prometheus: Scrape Target Blue-Green (PR #41)

**Temuan** (dari audit): target `lazisnu-backend` DOWN — `lookup green-backend: no such host`.

**Akar masalah (2 lapis)**:
1. `prometheus/prometheus.yml` hanya menarget `green-backend:3101` (keputusan Sesi 03, commit `2df92ef` — target `backend:3001` dihapus). Port 3101 = `BACKEND_PORT_GREEN`; port blue = 3001.
2. `deploy-blue-green.sh` menulis ulang `nginx/upstream.conf` tapi **tidak pernah menyentuh prometheus.yml** → sejak deploy v1.0.2 (2026-08-04, warna aktif = BLUE), green di-teardown → target mati → monitoring backend kosong.

**Perbaikan (Opsi A)**: pasang **dua target sekaligus** — warna idle down (normal, non-fatal), up kembali saat di-switch:
```yaml
- targets: ["blue-backend:3001", "green-backend:3101"]
```

**Rollout & pelajaran**: `docker compose up --force-recreate prometheus` gagal (rebuild image tak sengaja) → gunakan **`docker restart`**. SIGHUP reload **tidak cukup** setelah `git checkout -f` (git mengganti file → bind mount masih menunjuk inode lama) → `docker restart` re-mount ke inode baru.

**Verifikasi**: `blue-backend:3001` up, `green-backend:3101` down (normal), 33 series `http_requests_total` ter-scrape. Detail lengkap: `SESSION-2026-08-07.md` §8.

## 4. Investigasi Notifikasi UP Hilang → Upgrade Uptime Kuma 2.x (PR #46)

**Gejala user**: Kuma kirim notif DOWN "Staging API went down" tapi notif UP tidak pernah datang.

**Investigasi (fakta dari VM)**:
- Staging API **sehat** (200) sejak 05:15 WIB; down terakhir hanya 2 menit (502 di 05:13 WIB).
- Kuma **mendeteksi** transisi up (`heartbeat important=1`) — jadi masalah bukan deteksi.
- Webhook Discord **sehat** (test POST → HTTP 204).
- Root cause: bug Uptime Kuma **1.23.17** — notifikasi yang gagal/terlewat **tidak pernah di-retry** ([louislam/uptime-kuma#6046](https://github.com/louislam/uptime-kuma/issues/6046)).

**Pilihan user**: Opsi B — upgrade permanen ke `louislam/uptime-kuma:2` (v2.5.0).

**Insiden migrasi**: v2 crash-loop `Aggregate table migration is already in progress`.
- Akar: DB berisi **5794 heartbeat orphan** + 3 `monitor_tls_info` dari monitor id 1–5 yang sudah dihapus (setup ulang Kuma ke id 10–13) → migrasi agregat v2 gagal FK → state `migrateAggregateTableState="migrating"` macet.
- Solusi: backup DB gagal → restore DB v1 asli (backup pre-upgrade) → hapus orphan FK → start v2 → migrasi bersih. `PRAGMA foreign_key_check` = 0.

**Verifikasi end-to-end (down→up nyata)**:
- Stop `backend-staging` → Kuma deteksi DOWN (502, 11:33:30) → **notif DOWN masuk Discord** ✅
- Start `backend-staging` → Kuma deteksi UP (`important=1`, 11:35:30) → **notif UP masuk Discord** ✅
- Bug #6046 tuntas. Detail: `SESSION-2026-08-07.md` §8.2.

## 8. Sesi Lanjutan (Sore) — Akses Publik Grafana + Root Cause Alert Heap False Positive

> Sesi lanjutan di hari yang sama. User menerima notif Discord `HighHeapMemoryUsage` berulang (firing↔resolved, nilai 86–90%) dan bertanya artinya. Investigasi berujung pada 2 pekerjaan besar: **(1)** mempublikasikan Grafana via subdomain (sebelumnya hanya bisa lewat SSH tunnel), **(2)** membongkar root cause alert heap → perbaikan rule + template Discord. Semua terverifikasi langsung di VM.

### 8.1 Akses Publik Grafana (grafana.lazisnu.site)

**Masalah**: Grafana bind `127.0.0.1:3030` → akses hanya lewat SSH tunnel.

**Solusi** (pola sama dengan `status.lazisnu.site` → Uptime Kuma):
- DNS A record `grafana → 43.128.98.52` (panel Hostinger, dilakukan user).
- `nginx/nginx.conf`: blok HTTP (redirect + acme-challenge) → issue cert via certbot webroot → blok HTTPS proxy ke `grafana:3000` + `limit_req zone=grafana` (10r/s, cegah brute force login).
- Password Grafana diganti dari default (`GRAFANA_ADMIN_PASSWORD` di `.env` VM).

**⚠ Pelajaran kunci (bind-mount inode stale)**: setelah `git pull`, container nginx ternyata masih melayani config LAMA — **bind mount file tunggal mengunci inode lama** saat git mengganti file (write-temp + rename), `nginx -s reload` tidak cukup. Solusi: **`docker restart lazisnu-nginx-1`** agar mount mengikuti inode baru. Gejala khasnya: config baru sukses di `nginx -t` host, tapi `nginx -T` di container tetap config lama. Berlaku sama untuk prometheus/alertmanager (semua bind-mount file `.yml`/`.tmpl`).

### 8.2 Insiden: Login Grafana "invalid username and password"

- **Akar masalah**: Grafana v13.1.1 menolak hash password **legacy** (PBKDF2 50-byte hex + kolom `salt` terpisah) yang dibuat versi lama → berapa pun passwordnya selalu 401.
- `grafana cli admin reset-admin-password` tampil "changed successfully" tapi **hash di DB tidak berubah** (v13 menulis ke tempat lain) → bukan solusi.
- **Solusi**: DB lama di-backup (`grafana.db.legacy-20260808-192145`, `grafana.db.bak-20260808-192018`), biarkan Grafana v13 membuat DB + admin baru dari env → `Created default admin user=admin` → login sukses. Dashboard `Lazisnu Overview` + datasource Prometheus ter-provision ulang otomatis dari file repo.
- Catatan: `POST /api/login` via curl 401 (`handler=notfound`) karena **endpoint API login deprecated di v13** — login UI normal (diverifikasi browser).

### 8.3 Verifikasi Dashboard Lazisnu Overview

- Panel saat dicek: Memory RSS **91.4 MB**, Heap Used **44.2 MB**, CPU **0.24%**, Event Loop **5.67 ms**; grafik time series memory & CPU ter-render dengan data.
- 5 panel kosong (HTTP Request Rate, HTTP Error Rate, Active Handles/Requests, Open FD) — **normal**: metrik custom (`http_requests_total`, dll) belum di-expose backend. Alert `HighHttpErrorRate` juga masih menganggur karena alasan yang sama.

### 8.4 Root Cause Alert HighHeapMemoryUsage (false positive)

**Gejala**: alert firing 86–90% hampir terus-menerus (rasio 75–89% sepanjang 6 jam) padahal heap used hanya ~45 MB.

**Akar masalah — kesalahan rumus**:
- `nodejs_heap_size_total_bytes` = heap yang **sedang di-commit V8** (bukan limit). V8 hanya meng-commit heap sedikit di atas yang terpakai → rasio `used/total` hampir selalu 75–90% pada aplikasi sehat.
- `nodejs_heap_size_limit_bytes` **tidak di-expose** prom-client versi yang dipakai → tidak ada denominator yang benar.
- **Bukti**: `v8.getHeapStatistics()` di container → `heap_size_limit = 2052 MB`; heap used = **2.2% dari limit**. Bukan leak — salah ukur. (Rasio stabil = bukti tambahan tidak ada pertumbuhan leak.)

**Fix** (Opsi absolut, tanpa ubah kode backend): rule pakai ambang absolut
`nodejs_heap_size_used_bytes > 1700e6` (>85% dari limit 2GB). State setelah deploy: **inactive**.

### 8.5 Fix Link Discord Mati + Template Notifikasi

- Link `http://f8cfe037fdb4:9090/graph?...` di notif = **hostname internal container** (Prometheus/Alertmanager di docker network) → tidak bisa dibuka publik.
- Fix: custom template inline di `alertmanager/alertmanager.yml.tmpl` (title `[FIRING]/[RESOLVED]` + labels/annotations + **link dashboard Grafana** yang bisa diklik).
- **⚠ Pelajaran**: log "Notify success" alertmanager v0.33 ber-level **DEBUG**, bukan INFO — verifikasi dispatch harus `--log.level=debug`, kalau grep level INFO hasilnya kosong & seolah-olah tidak mengirim.
- **Verifikasi E2E**: POST webhook langsung → HTTP 204; test alert → log `Notify success receiver=discord attempts=1 duration=405ms`.

### 8.6 Pelajaran Teknis Lintas (accumulated)

1. Bind mount file tunggal + git checkout/pull → **inode stale** → restart container (nginx/prometheus/alertmanager), bukan sekadar reload.
2. PowerShell 5 here-string mengirim **CRLF** → pipe ke `ssh ... bash -s` harus lewat `tr -d '\r'`; pakai `curl.exe` (alias `curl` = Invoke-WebRequest). Gejala: `--since 90s\r`, `no such service: grafana\r`.
3. Encoding console: output UTF-8 dari VM tampil `ΓÇö` di PowerShell 5 (ANSI) — data tidak rusak.
