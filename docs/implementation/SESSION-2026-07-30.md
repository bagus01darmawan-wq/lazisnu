## 3. 08-B2 / 07-E2-3 — Test Restore Backup Pertama

### Root Cause (Attempt 1 & 2 — Gagal)
- `pg_dump` tanpa flag `--schema=public` → dump semua schema Supabase internal
- Restore gagal karena schema (`auth`, `drizzle`, dll) sudah ada di staging → `CREATE TABLE` error → `COPY` data tidak dieksekusi

### Fix: Perbarui `scripts/backup.sh`

```bash
# Sebelum:
pg_dump "$DIRECT_URL"

# Sesudah:
pg_dump \
  --schema=public \
  --no-owner \
  --no-acl \
  --clean \
  --if-exists \
  "$DIRECT_URL"
```

- `--schema=public` → hanya schema aplikasi
- `--no-owner --no-acl` → tidak dump permission Supabase
- `--clean --if-exists` → tambah `DROP TABLE IF EXISTS` → restore idempotent ke DB yang sudah punya schema

```

```

- Container mount **file** bukan **direktori**: `./backup-active:/app/backup-active`
- Docker file bind-mount tidak bisa di-`unlink()` dari dalam container

### Fix: Ganti ke Directory Mount

```yaml
# docker-compose.yml — sebelum:
volumes:
  - ./backup-active:/app/backup-active
environment:
  - BACKUP_FLAG_PATH=/app/backup-active

# Sesudah:
volumes:
  - ./backup-data:/app/backup-data
environment:
  - BACKUP_FLAG_PATH=/app/backup-data/active
```

- Buat direktori `/opt/lazisnu/backup-data/` di VM
- Migrate flag: `cp backup-active backup-data/active`

### Backend (commit `ebf29b0`)

export const httpRequestDurationMs = new promClient.Histogram({
  name: 'http_request_duration_ms',
  help: 'Duration of HTTP requests in ms',
  labelNames: ['method', 'route', 'statusCode'],
  buckets: [5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000],
});
export const httpRequestsTotal = new promClient.Counter({
  name: 'http_requests_total',
  help: 'Total HTTP requests',
  labelNames: ['method', 'route', 'statusCode'],
});
```

**`apps/backend/src/app.ts`** — tambah onResponse hook kedua (samping `auditLogger`):

server.addHook('onResponse', async (request, reply) => {
  const route = (request.routeOptions?.url as string | undefined) ?? 'unmatched';

  httpRequestDurationMs.labels(labels).observe(reply.elapsedTime);
  httpRequestsTotal.labels(labels).inc();
});
```
- Pakai `routeOptions.url` (template `/v1/users/:id`) bukan `req.url` (instance `/v1/users/123`) untuk hindari cardinality explosion

# Sesi 30 (Lanjutan 4) — Rate-Limit 500 → 429 Fix ✅

## Latar Belakang

Backlog Sesi 31 #1: **Rate-limit Fastify `TOO_MANY_REQUESTS` dilempar sebagai unhandled error → HTTP 500, seharusnya 429.**

Dampak ke klien (web/mobile): tidak bisa membedakan "saya kena rate limit" vs "server error" → retry agresif atau anggap sebagai bug, mobile app bisa stuck di loading loop.

## Investigasi 3 Langkah

### Step 1 — Reproduce bug
Bombard `/v1/auth/login` 110x dari VM (max 5/menit per-route). Hasil:
- 0× HTTP 429
- **105× HTTP 500**
- Header benar: `x-ratelimit-limit: 5`, `x-ratelimit-remaining: 0`, `x-ratelimit-reset: 53`, `retry-after: 53`
- Body: `{"success":false,"error":{"code":"INTERNAL_ERROR","message":"Terjadi kesalahan server"}}`

### Step 2 — Backend logs
Log green-backend menunjukkan:
```json
"err":{"success":false,"error":{"code":"TOO_MANY_REQUESTS","message":"..."}}
"msg":"Unhandled error"
"res":{"statusCode":500}
```

**Akar masalah**: `errorResponseBuilder` di `app.ts` line 54-62 return plain object `{success:false, error:{code, message}}` (TANPA `statusCode: 429`). Plugin `@fastify/rate-limit` melempar object ini sebagai error. Branch `error.statusCode === 429` di `setErrorHandler` → **FALSE** (statusCode undefined) → fallback 500.

### Step 3 — Per-route config
Cek `routes/auth.ts`:
- `/v1/auth/login`: max 5/menit
- `/v1/auth/request-otp`: max 3/menit
- `/v1/auth/verify-otp`: max 5/menit
- `/v1/auth/refresh`: max 30/5 menit
- `/v1/auth/logout`: max 10/5 menit
- Global default: 100/menit

Semua endpoint dengan rate limit custom kena bug yang sama.

## Fix

**`apps/backend/src/app.ts`** (line 165-174) — tambah deteksi via `error.error.code`:

```ts
// 5. Rate limit error (from @fastify/rate-limit)
// errorResponseBuilder return plain object {success:false, error:{code:'TOO_MANY_REQUESTS',...}}
// yang dilempar sebagai error. Object ini TIDAK punya statusCode.
// Fix: deteksi via `error.error.code === 'TOO_MANY_REQUESTS'` (object shape
// dari errorResponseBuilder) ATAU `error.statusCode === 429` (default behavior).
const errAny = error as unknown as Record<string, unknown>;
const innerError = errAny.error as { code?: string } | undefined;
const isRateLimit =
  errAny.statusCode === 429 ||
  innerError?.code === 'TOO_MANY_REQUESTS';
if (isRateLimit) {
  return reply.status(429).send({
    success: false,
    error: {
      code: 'TOO_MANY_REQUESTS',
      message: 'Terlalu banyak permintaan, silakan coba lagi nanti',
    },
  });
}
```

**`apps/backend/src/routes/__tests__/auth.integration.test.ts`** — tambah test case:
```ts
describe('Rate Limit (Backlog Sesi 31 #1)', () => {
  it('harus return 429 (bukan 500) saat /v1/auth/login kena rate limit', async () => {
    // Bombard 7x — req 6-7 harus 429 + TOO_MANY_REQUESTS
    const app = await getApp();
    const results = [];
    for (let i = 0; i < 7; i++) {
      const res = await request(app.server).post('/v1/auth/login').send(VALID_ADMIN);
      results.push({ status: res.status, code: res.body?.error?.code });
    }
    const rateLimited = results.slice(5);
    for (const r of rateLimited) {
      expect(r.status).toBe(429);
      expect(r.code).toBe('TOO_MANY_REQUESTS');
    }
    expect(results.find(r => r.status >= 500)).toBeUndefined();
  });
});
```

# Sesi 30 (Lanjutan 10) — SOP Mount Bind File (Backlog Sesi 31 #6)

> Status: SELESAI ✅ | File: `docs/SOP-MOUNT-BIND-FILE.md` (commit `d322fd0`)

## Latar Belakang

SOP ini dibuat untuk:
1. **Onboarding developer baru** — acuan standar saat me-mount file/dir ke container
2. **Troubleshooting reference** — panduan saat terjadi error (permission, file not found, dll)
3. **Prevent insiden** — encode lessons-learned dari Sesi 31 (chown Sesi 31) dan Sesi 30 (Lanjutan 5 fix-volume-ownership)

## Konten SOP

| Section | Topik |
|---------|-------|
| 1 | Kapan pakai bind mount vs Docker volume (prinsip) |
| 2 | Konvensi proyek (path, mode, naming) |
| 3 | Step-by-step tambah config baru (contoh blackbox-exporter) |
| 4 | Verifikasi mount berhasil (mount point, permission, write test) |
| 5 | Troubleshooting 5 kasus umum |
| 6 | Pitfall umum 6 kasus (CRLF, tab, absolute path, lupa :ro, conflict, spasi) |
| 7 | Recap perubahan bind mount (audit trail) |
| 8 | Referensi ke SOP lain |

## Highlight Penting

### Prinsip (Section 1)
- **Config & static asset** → bind mount (tracked di git)
- **Data dinamis** → Docker volume (performance, snapshot)

### Konvensi (Section 2)
- SELALU tambahkan `:ro` untuk config file (`.yml`, `.conf`)
- Gunakan relative path `./xxx`, BUKAN absolute `/home/ubuntu/...`
- Naming: lowercase-hyphen, descriptive (`redis.conf` bukan `config.yml`)

### Pitfall yang Harus Dihindari (Section 6)
1. **CRLF vs LF** — diedit di Notepad Windows → container `'\r': command not found`
2. **Tab vs spasi** — YAML/JSON strict
3. **Absolute path** — tidak portable
4. **Lupa `:ro`** — security risk
5. **Volume conflict** — nama sama antara volume & bind mount = silent conflict
6. **Spasi di nama file** — escape hell di PowerShell/Docker

## TD-01 — Refactor Mock DB Global di `auth.integration.test.ts`

### Akar Masalah

Mock DB di-top-level (line 12) menciptakan **singleton** yang dishare ke semua test dalam file. Pattern lama:

```ts
beforeEach(() => {
  jest.clearAllMocks();  // HANYA hapus call history
});
```

`jest.clearAllMocks()` menghapus mock call history (`mock.calls`, `mock.results`), **BUKAN reset implementation** yang sudah di-set dengan `.mockImplementation()` atau `.mockReturnValue()`. Akibatnya:

- Test A set `db.select.mockImplementation(() => mockA)` → return mockA
- Test B dipanggil → `db.select` masih return mockA (dari Test A) karena impl tidak di-reset
- Test B expects mockB → MISMATCH → test gagal

Ini adalah TD-01 yang sudah terdokumentasi: test Session Management **lulus saat dijalankan terisolasi** (`jest -t "Session Management"`) tapi **2 dari 3 gagal saat dicampur** dengan outer tests.

### Pendekatan Fix

1. **Ganti `jest.clearAllMocks()` → `jest.resetAllMocks()`** di **4 beforeEach** (line 90, 163, 220, 259, 320 + 2 tambahan).
2. **Tambah beforeEach** di 2 describe yang belum punya: `verify-otp` (line 206) dan `logout` (line 298) — agar `setupDefaultDbMocks()` selalu dipanggil.
3. **Re-establish default mock** via helper `setupDefaultDbMocks()` setelah reset:
   - `db.select()` chain → return array kosong `[]` (awaitable)
   - `db.update().set().where()` → return `[{}]`
   - `db.insert().values()` → return `[{}]`
   - `db.query.users.findFirst` / `db.query.officers.findFirst` → `mockReset()` (return undefined)

### Kode Hasil

```ts
// Helper — dipanggil setelah jest.resetAllMocks() di setiap beforeEach
const setupDefaultDbMocks = () => {
  (db.select as jest.Mock).mockImplementation(() => ({
    from: jest.fn().mockImplementation(() => ({
      where: jest.fn().mockImplementation(async () => []),
    })),
  }));
  (db.update as jest.Mock).mockImplementation(() => ({
    set: jest.fn().mockImplementation(() => ({
      where: jest.fn().mockImplementation(async () => [{}]),
    })),
  }));
  (db.insert as jest.Mock).mockImplementation(() => ({
    values: jest.fn().mockImplementation(async () => [{}]),
  }));
  (db.query.users.findFirst as jest.Mock).mockReset();
  (db.query.officers.findFirst as jest.Mock).mockReset();
};

// Pattern baru di 6 beforeEach
beforeEach(() => {
  jest.resetAllMocks();
  setupDefaultDbMocks();
});
```

## TD-03 — Drizzle Auto-Sync Test DB

### Akar Masalah

`drizzle-kit push` (script `migrate` di package.json line 17) **tidak reliable** untuk deteksi drift di test DB:

- Setelah schema berubah (e.g. tambah kolom `users.fcm_token` atau `user_sessions.device_id`), test DB tidak auto-sync
- `push` reconcile schema langsung ke DB tanpa file tracking
- Untuk drift detection, butuh compare dengan schema di file — `push` tidak melakukan ini dengan benar di test DB
- Akar masalah: `push` cocok untuk prototyping, **bukan untuk environment yang harus reproducible** (test/CI)

### Pendekatan Fix

1. **Tambah script `db:reset-test`** di `package.json`:
   ```json
   "db:reset-test": "bash scripts/db-sync-test.sh"
   ```

2. **Buat script `apps/backend/scripts/db-sync-test.sh`** (idempotent, ~90 baris):
   - **Step 1**: Drop schema `public` + recreate + grant (via `psql`)
   - **Step 2**: Apply migration files via `drizzle-kit migrate` (bukan push) — reliable, tracked
   - **Step 3**: Verify table count ≥ 5 (sanity check)
   - **Step 4**: List applied migration files (audit trail)

3. **Idempotent**: Aman di-run berulang — `DROP SCHEMA IF EXISTS` + recreate + apply migrations menghasilkan state yang sama setiap kali.

### Kode Hasil (Script Head)

```bash
#!/usr/bin/env bash
set -euo pipefail
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
cd "${SCRIPT_DIR}/.."

# Load .env.test
set -a; source .env.test; set +a

# Step 1: Drop & recreate schema
psql "${DATABASE_URL}" -c "DROP SCHEMA IF EXISTS public CASCADE;" \
                        -c "CREATE SCHEMA public;" \
                        -c "GRANT ALL ON SCHEMA public TO public;"

# Step 2: Apply migrations (reliable, tracked)
DATABASE_URL="${DATABASE_URL}" npx drizzle-kit migrate --config=drizzle.config.ts

# Step 3-4: Verify + list
```
