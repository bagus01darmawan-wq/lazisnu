## DESAIN YANG DIMINTA (mengikat)

### A. Co-sign per sesi (menghapus celah spoof id)

Aturan induk (§14.6, KEPUTUSAN C-3): **`signer_id` = pemilik sesi login
masing-masing, bukan pilihan dari body**. Artinya `ppk_signer_id` /
`bendahara_signer_id` / `ranting_signer_id` / `mwc_bendahara_signer_id`
**dilarang** datang dari klien lagi.

**Tingkat 1 (PPK ↔ bendahara ranting):**
- `POST /v1/mobile/submissions/:id/sign` — sesi **PETUGAS pemilik setoran**
  (user login yang `officerId`-nya = `officer_id` submission).
  Body: `{ signature_png (base64 PNG), consent: true, expected_version }`.
  Efek: validasi PNG + consent → upload coretan ke R2 (key acak) →
  `ppk_signer_id = userId sesi` (server), `ppk_signed_at`, `ppk_signature_url`
  → status `DRAFT → PPK_SIGNED` → audit. Sudah PPK_SIGNED/FINAL → `CONFLICT`.
- `POST /v1/mobile/submissions/:id/countersign` — sesi **STAF_KEUANGAN**.
  Scope **WAJIB**: tier-1 = `branchId` sesi sama dengan `branch_id` submission
  (temuan review-T4 #1 — T4 hanya cek peran, ini yang kamu tutup).
  Body: `{ signature_png, consent: true, expected_version }`.
  Efek: `bendahara_signer_id = userId sesi`, `bendahara_signed_at`,
  `bendahara_signature_url`; lalu evaluasi FINAL **satu transaksi**:
  kedua TTD terisi + beda userId + `version` cocok + sisa `ACTIVE` = 0 →
  `FINAL` (+`finalized_at/by`). Bila masih ada ACTIVE → tetap `PPK_SIGNED`
  (kedua TTD tercatat) dan balas pesan bahwa Admin Ranting harus
  **force + alasan**.
- `POST /v1/mobile/submissions/:id/force-finalize` — sesi **ADMIN_RANTING
  pemilik ranting**; body `{ force_reason (min 5), expected_version }`.
  Prasyarat (menolak bila tidak): status `PPK_SIGNED` **dan kedua TTD sudah
  tercatat**. Efek: `FINAL` + audit `forced=true` + alasan. Force hanya
  menimpa gerbang ACTIVE — **tidak pernah** menimpa syarat dua TTD (§9.1).
- Jalur lama `POST /submissions/:id/finalize` (yang menerima dua signer id dari
  body) **diganti** kontrak di atas. Test T4 tentang varian signer-ditolak
  diubah menyesuaikan (cakupannya jangan hilang — tambah varian "keuangan
  ranting lain → 403" dan "signer bukan sesi → ditolak").

**Tingkat 2 (ranting ↔ MWC):**
- `POST /v1/admin/branch-submissions/:id/sign` — sesi **ADMIN_RANTING
  pemilik**. Body: `{ signature_png, consent: true, expected_version,
  share_mwc, variance_reason?, linked_periods?, as_nol? }`. Gerbang T4 tetap
  berlaku (semua PPK FINAL — tolak sambil sebut nama; selisih >10rb wajib
  alasan; GABUNG_PERIODE wajib `linked_periods`; FINAL_NOL total 0 + alasan).
  Efek: hitung + validasi T4 → `ranting_signer_id = userId sesi` +
  `ranting_signed_at` + coretan R2 → status **tetap `DRAFT`** (menunggu MWC).
- `POST /v1/mobile/branch-submissions/:id/countersign` — sesi
  **STAF_KEUANGAN satu distrik** dengan ranting (MWC; `districtId` sesi =
  `district_id` submission). Beda userId dengan penandatangan ranting
  ditegakkan server + CHECK DB. Efek: `mwc_bendahara_signer_id = userId sesi`
  → `FINAL` atau `FINAL_NOL` (sesuai `as_nol` yang sudah tervalidasi) + audit.

### B. BA teks readable (dari snapshot — bukan hitung ulang)

- `GET /v1/mobile/submissions/:id/berita-acara` (pemilik, STAF_KEUANGAN
  seranting, ADMIN_RANTING pemilik, ADMIN_KECAMATAN sedistrik) dan
  `GET /v1/admin/branch-submissions/:id/berita-acara`.
- Isi BA-PPK (§10): kop LAZISNU, periode, nama PPK + ranting, tabel
  `total, bisyaroh, bersih, jumlah kaleng`, pernyataan penyerahan, status
  kedua TTD. BA-Ranting: agregat format WA + daftar PPK penyusun
  (nama + total) + pernyataan + status TTD.
- Sebelum FINAL yang tampil hanya **"DRAFT — belum sah"** (§10 aturan tampil).
- Sumber = snapshot di baris submission. **Jangan** kolom baru; cukup derive.

### C. PDF lazy + hash + QR verifikasi

- `GET /v1/mobile/submissions/:id/pdf` & `GET /v1/admin/branch-submissions/:id/pdf`
  (peran sesuai A/B). **Hanya setelah `FINAL`/`FINAL_NOL`**; sebelum itu tolak
  jelas ("BA belum sah — belum kedua TTD").
- Generate **saat unduh** dari snapshot + 2 gambar coretan TTD dari R2
  (ambil via key, bukan URL publik) + QR verifikasi; pola `qrPdfService.ts`
  (`pdf-lib` + `qrcode` + `uploadToR2`).
- `pdf_url` = **key R2** (bukan URL publik); `pdf_hash` = SHA-256 hex dari
  bytes PDF. Key berversi & acak:
  `ba-pdfs/{ppk|branch}/{submissionId}/v{version}-{uuid}.pdf`.
- Idempoten: `version` sama & `pdf_url`+`pdf_hash` sudah terisi → jangan
  generate ulang (kecuali flag force). Setiap unduhan: `getSignedDownloadUrl`
  umur pendek + audit `activity_logs` (mis. `BA_DOWNLOADED`).
- **FINAL tidak boleh bergantung R2**: bila upload/generate gagal, FINAL tetap
  sah — balas pesan berkas belum siap, dicoba lagi saat unduh berikutnya
  (§14.10). Boleh sederhana, asal tidak menggagalkan FINAL.
- **Verifikasi QR minimal** (§14.9 + tinjauan C-6): endpoint publik
  `GET /v1/verify/ba?type=ppk|branch&id=&version=&hash=` → `{ valid: bool }`
  saja. **Dilarang** membocorkan nominal, nama pihak, atau keberadaan id
  (balasan seragam untuk id tak dikenal). Cek pola privasi
  `middleware/__tests__/scan-qr.test.ts`.

### D. R2 privat-rasa-publik + consent TTD (UU 27/2022)

- Bucket privat: tanpa URL publik di DB, key acak tak tertebak
  (`{uuid}.png` / `v{version}-{uuid}.pdf`), akses hanya via signed URL
  berumur pendek + `Cache-Control: private` + audit tiap unduhan.
- Validasi coretan: PNG saja (magic bytes `89 50 4E 47`), ≤ 50KB, base64
  valid; tolak selain itu `VALIDATION_ERROR`. Simpan via `uploadToR2`
  (`contentType: image/png` + metadata submission).
- **Consent wajib**: `consent: true` + catat jejak consent (versi teks, ip,
  user-agent) di `activity_logs` saat menandatangani. Tanpa consent → tolak.
- Mekanisme hapus (retensi): fungsi service `purgeSignatureFile(key)` +
  endpoint admin terbatas beralasan + audit yang memanggil `deleteFromR2`
  (`r2.ts:92`). Bila ditunda, **nyatakan eksplisit** di laporan (jangan diam).

### E. Non-fungsional (wajib)

- Semua transisi: `expected_version` optimistik + `CONFLICT` 409, 1 transaksi,
  race-safe (`UPDATE … WHERE status/version` + cek baris terpengaruh).
- Tambahkan `FOR UPDATE` pada baris submission di `assertSubmissionOpen`
  (`collectionSubmission.ts`) — syarat review-T4 #2, murah, menutup balapan
  submit↔finalize.
- Role-guard & scope **di server**, bukan UI.
- **Tanpa migrasi**: enum `ppk_submission_status` sudah memuat `PPK_SIGNED`
  sejak T0 (`schema.ts:17`) dan kolom `*_signature_url` + `pdf_hash` sudah ada
  di kedua tabel. Bila kamu merasa butuh kolom/migrasi baru → **hentikan dan
  laporkan alasannya**, jangan tambah diam-diam.
