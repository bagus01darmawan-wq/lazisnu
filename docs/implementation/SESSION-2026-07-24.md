## Bug yang Ditemukan & Diperbaiki

### Bug 1: Login berhasil tapi tidak redirect ke dashboard (P0)

**Root cause:** `middleware.ts` web pakai `JWT_SECRET` (lama) untuk verify token, padahal backend sudah sign pakai `JWT_ACCESS_SECRET` (baru, dari Sub-bab 02).

**Efek:**
- User login → backend return 200 → cookie diset → `router.push('/dashboard')`
- Middleware verify token gagal → cookie dihapus → redirect balik ke `/login`
- User pikir login gagal → klik berulang → kena rate limit 5x/menit

**Fix:**
- [middleware.ts:21](apps/web/src/middleware.ts) — `JWT_SECRET` → `JWT_ACCESS_SECRET || JWT_SECRET` (fallback)

### Bug 2: Rate limit error tampil sebagai 500 (bukan 429)

**Root cause:** Rate limit error dari `@fastify/rate-limit` tidak ditangani dengan benar di global error handler. Fallback ke `sendInternalError` → 500.

**Fix:**
- [app.ts](apps/backend/src/app.ts) — tambah handler khusus untuk `error.statusCode === 429` → return `sendError(429, 'TOO_MANY_REQUESTS')`

### Bug 3: Dashboard 404 "This page could not be found"

**Root cause:** API call dari dashboard (`/v1/admin/district/dashboard`) diarahkan ke Next.js oleh nginx karena dashboard server block tidak punya proxy `/v1/` ke backend.

**Efek:**
- Halaman overview kosong (tidak ada data statistik)
- Halaman lain OK karena pakai client-side Axios yang fallback ke `NEXT_PUBLIC_API_URL`

**Fix:**
- [nginx.conf](nginx/nginx.conf) — tambah `location /v1/ { proxy_pass http://backend:3001; }` di SSL Web server block

### Bug 4: Halaman laporan kosong

**Root cause:** Reports page pakai server-side fetch (`process.env.NEXT_PUBLIC_API_URL`), tapi variabel ini tidak diset di web container → fallback ke `http://localhost:3001` → tidak bisa resolve.

**Fix:**
- [docker-compose.yml](docker-compose.yml) — tambah `NEXT_PUBLIC_API_URL=http://backend:3001` di web service environment
- [Dockerfile](apps/web/Dockerfile) — tambah `ARG NEXT_PUBLIC_API_URL` + `ENV NEXT_PUBLIC_API_URL=$NEXT_PUBLIC_API_URL`

## Bagian 2 — Perencanaan Redis Lokal (📋 Direncanakan)

### Temuan

Upstash Redis free tier tidak layak untuk production karena:

- Limit 500.000 request/bulan — habis oleh polling BullMQ worker saja
- Worker WhatsApp polling `BZPOPMIN` setiap ~10 detik → 259.200 request/bulan → belum termasuk operasi Redis lain (session store, OTP, dll)

### Keputusan

Ganti Redis dari **Upstash (cloud)** ke **Redis container di VM** dengan konfigurasi:

| Fitur | Konfigurasi |
|-------|-------------|
| Image | `redis:7-alpine` |
| Persistensi | AOF (Append Only File) — catat setiap operasi tulis |
| Snapshot | RDB tiap 5 menit (atau 60 detik jika 10+ perubahan) |
| Volume | `./redis-data:/data` — data tersimpan di disk host VM |
| Auto-restart | `restart: unless-stopped` + healthcheck |
| Max memory | 50 MB, policy `volatile-lru` |

### Data di Redis & Dampak Kehilangan

| Data | Jika Hilang | Kritis? |
|------|-------------|:---:|
| Refresh token (`refresh:{userId}:{deviceId}`) | User login ulang | ❌ |
| Device registry (`refresh:devices:{userId}`) | Revoke massal gagal | ❌ |
| BullMQ WhatsApp jobs | Notifikasi WA hilang sementara | ⚠️ |
| OTP codes (`otp:{phone}`) | Request OTP ulang | ❌ |
| OTP rate limit | Reset sementara | ❌ |

**Tidak ada data finansial di Redis.** Semua data collection tersimpan di PostgreSQL (Supabase).

### Dampak ke Offline Collection

**Tidak ada.** Penjemputan offline menyimpan data ke MMKV (HP) → sync ke PostgreSQL. Redis hanya dipakai untuk:
1. Notifikasi WA (setelah collection tersimpan, via BullMQ)
2. Refresh token (kenyamanan, tidak wajib untuk sync)

Collection tersimpan dulu ke Supabase, baru WA dikirim. Kalau WA gagal, collection tetap sukses (dengan status `whatsapp_status: FAILED`).

### Prinsip Kuitansi Digital

Notifikasi WA BUKAN bonus — ini adalah **kuitansi digital** yang harus tersampaikan ke donatur. Mekanisme:

1. **Retry otomatis 10x** oleh worker (exponential backoff: 3→6→12→24→48→96→192→384→768→1536 detik, total ~30 menit)
2. **Retry manual oleh admin** (`ADMIN_CABANG`, `ADMIN_RANTING`) via endpoint API + UI di dashboard WA Monitor
3. **Log permanen** di tabel `notifications` (PostgreSQL) — status `SENT` atau `FAILED`

| Fitur | Konfigurasi |
|-------|-------------|

| Persistensi | AOF (Append Only File) — `appendfsync everysec` |

| Max memory | 50 MB, policy `volatile-lru` |
| Auto-restart | `restart: unless-stopped` |

### Dependensi Container

- `backend` & `worker`: `depends_on: redis (condition: service_healthy)`
- `REDIS_URL` di-override via environment docker-compose: `redis://redis:6379`
- `.env` VM yang lama (Upstash) tetap terbaca oleh `env_file`, tapi di-override oleh `environment` di docker-compose

### Retry BullMQ: 3x → 10x

| Parameter | Sebelum | Sesudah |

| `attempts` | 3 | 10 |
| `backoff.delay` | 5000ms | 3000ms |
| Progression delay | 5s→10s→20s | 3s→6s→12s→24s→48s→96s→192s→384s→768s |
| Total retry window | ~35 detik | ~25.5 menit |
