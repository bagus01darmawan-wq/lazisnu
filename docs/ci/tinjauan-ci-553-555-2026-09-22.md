## Sebab #555 (yang diperbaiki di `a6ee133`)

```ts
// sebelum — TS2367
.findAll(node => typeof node.type === 'string' && node.type === 'Text')

// sesudah — pola yang sudah dipakai tes mobile lain
tree.root.findAllByType(Text).map(node => collectText(node.props.children))
```

`ElementType` dari `@types/react` menyempitkan `string` ke `keyof JSX.IntrinsicElements`
(daftar tag HTML), yang tidak memuat `'Text'` — jadi perbandingan itu dianggap mustahil
oleh TypeScript. **Perilaku runtime-nya sebenarnya benar**; ini positif palsu di level tipe.
Karena itu perbaikannya bukan menambal `as any`, melainkan memakai `findAllByType(Text)`
seperti `SyncIssuesSheet.test.tsx` dan `TaskDetailScreen.test.tsx`.

### Satu assertion backend yang berisiko — sudah diuji terpisah

`mobileRoles.integration.test.ts` memuat angka tanggal yang di-*hardcode* dari K1
(`T0 = 28 Sep 2026`, `period_status = TOLERANCE`, `days_to_due = 0`, `days_to_lock = 12`).
Tes itu butuh DB sehingga tidak bisa dijalankan penuh di sini, **tetapi** fungsi yang
menghasilkan angka-angka itu (`getPeriodInfo` di `services/mobileRoles.ts`) murni tanggal
dan tanpa DB — jadi bisa diuji sendiri lewat `tsx`. Hasilnya cocok persis dengan harapan tes
(`due_date` = 27 Sep 2026 23:59, `tolerance_end` = 9 Okt 2026 23:59). Karena `T0` adalah

Sisa tes backend tetap **belum terbukti** dan tidak bisa saya jamin dari sini.

(sama persis dengan perintah di CI, termasuk `-PabiFilter=arm64-v8a -PdisableFirebase=true`

Dua hal yang ikut diperiksa pada APK staging, karena keduanya bisa gagal tanpa terlihat:

- **Jalur berkas artifact cocok** — hasilnya di `app/build/outputs/apk/staging/debug/*.apk`,

  diperiksa: `https://staging-api.lazisnu.site` muncul 1×, `https://api.lazisnu.site` muncul **0×**.
  Jadi APK staging tidak akan diam-diam menghajar server produksi.

## Konsekuensi penting: memperbaiki CI saja TIDAK membuat T10 sampai ke staging

Perbaikan di `a6ee133` hanya menyentuh `apps/mobile/**` dan `docs/**`. Menurut kondisi job
di `ci.yml`, itu berarti:

| Job | Yang terjadi saat PR ini di-merge ke `staging` |
|---|---|
| `verify` | jalan (lint mobile, prettier mobile, typecheck) |
| `test-mobile`, `build-android-debug`, `build-staging-apk` | jalan |
| `test-backend`, `test-web` | ter-skip (backend/web tidak berubah) |
| `build-image` | **ter-skip** — butuh event `push` **dan** backend/web/infra berubah |
| `deploy-staging` | **ter-skip** — mensyaratkan `build-image.result == 'success'` |

Artinya **kode T10 (backend + web) masih belum akan ter-deploy ke staging** walau PR ini
sudah hijau dan ter-merge. Selama ini build image Docker untuk perubahan T10 memang
belum pernah berhasil sekali pun, karena #553 dan #555 berhenti sebelum job itu.

Jalan keluarnya satu: **`workflow_dispatch` pada workflow `CI` dengan ref `staging`**.
Pada event itu langkah `filter` tidak dijalankan, sehingga `decide` menandai **semua area
berubah** — `build-image` membangun ketiga image (backend, web-prod, web-staging) dan
`deploy-staging` ikut jalan. Ini sekaligus jadi kali pertama image T10 benar-benar dibangun.

> Catatan: dua cacat lama pipa ini — `paths-filter` yang meleset pada merge commit, dan
> `ci-status` yang menganggap `skipped` sebagai lolos — **sudah diperbaiki** di `ci.yml`
> (langkah `decide` menghitung ulang diff-nya sendiri; `ci-status` punya penjaga hijau
> palsu). Tidak perlu tindakan tambahan untuk keduanya.

## Catatan alat

- Log job GitHub Actions **tidak bisa diunduh tanpa autentikasi** (403) walau repo publik.
  Karena itu diagnosis dilakukan dengan **mereproduksi langkahnya di lokal** memakai perintah
  yang sama seperti di `ci.yml`.
- `prettier --check .` di laptop ini **gagal palsu** karena `core.autocrlf=true` (berkas kerja
  ber-CRLF). Diverifikasi dengan versi LF dari git — lolos, jadi CI tidak bermasalah.
