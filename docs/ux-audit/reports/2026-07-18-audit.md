## 3. Daftar Pain Point

| ID | Deskripsi | Platform | Severity | Bukti | Rekomendasi |
|---|---|---|---:|---|---|
| UX-01 | Daftar tugas mobile belum memberi CTA utama untuk langsung memulai penjemputan dari setiap item. Pada implementasi saat ini, item tugas hanya menampilkan informasi dan aksi salin QR, padahal mockup menampilkan tombol `Scan QR` yang lebih sesuai dengan alur kerja lapangan. Ini melanggar heuristic `recognition rather than recall` karena petugas dipaksa mengingat langkah berikutnya sendiri. | Native Android | 3 | `apps/mobile/src/screens/TasksScreen.tsx` pada komponen `TaskItem` hanya merender informasi + copy QR; mockup `docs/mockup-halaman-aplikasi-mobile/halaman-tugas.png` menampilkan CTA `Scan QR` per kartu tugas. | Jadikan `Scan QR` atau `Mulai Penjemputan` sebagai aksi primer pada kartu tugas, dan turunkan `copy QR` menjadi aksi sekunder. Pertahankan pola ini konsisten dengan shortcut di beranda. |
| UX-02 | Flow scan QR masih bisa buntu total saat offline jika kode belum pernah tersimpan di cache perangkat. Untuk konteks petugas lapangan, ini adalah risiko besar karena produk sudah menetapkan pendekatan offline-first. | Native Android | 4 | `apps/mobile/src/screens/ScanScreen.tsx` hanya mengizinkan fallback offline lewat `taskCache.findByQRCode(qrCode)`, lalu menampilkan alert "Hubungkan internet sekali" bila data belum ada. Rule `06-pedoman-mobile.md` menekankan mobile offline-first dan petugas bekerja di kondisi sinyal buruk. | Sinkronkan daftar QR dan metadata minimum sebelum shift dimulai, tampilkan status kesiapan offline yang lebih jelas, dan ubah pesan error menjadi langkah operasional yang bisa dilakukan petugas tanpa trial-and-error. |
| UX-03 | Halaman riwayat mobile berpotensi makin sulit dipindai saat volume transaksi bertambah karena implementasi saat ini belum menyediakan filter waktu cepat atau pencarian yang tampak di mockup. Koreksi data memang sudah ada, tetapi pencarian transaksi lama masih berat secara kognitif. | Native Android | 2 | `apps/mobile/src/screens/HistoryScreen.tsx` menampilkan daftar + modal koreksi, tetapi tidak terlihat kontrol filter cepat seperti di mockup `docs/mockup-halaman-aplikasi-mobile/halaman-riwayat.png` yang memiliki chip `Semua/Hari Ini/Minggu Ini/Bulan Ini` dan affordance pencarian. | Tambahkan filter periode cepat dan pencarian di bagian atas riwayat, lalu pertahankan penanda status sinkronisasi dan versi terbaru agar koreksi data lebih mudah ditemukan. |
| UX-04 | Halaman profil mobile belum memanfaatkan data profil yang lebih kaya dari backend, sehingga petugas tidak mendapat konteks wilayah, zona tugas, dan ringkasan performa pribadi. Ini menurunkan rasa orientasi dan kepercayaan bahwa akun yang dipakai memang akun yang benar. | Native Android | 2 | `apps/mobile/src/screens/ProfileScreen.tsx` hanya menampilkan nama, nomor HP, dan peran. Sementara `apps/mobile/src/services/api.ts` memiliki `getProfile()`, dan backend `apps/backend/src/routes/mobile/profile.ts` mengembalikan `branch`, `district`, `assigned_zone`, serta `stats`. | Tampilkan identitas kerja minimum: ranting, kecamatan, zona tugas, dan ringkasan total penjemputan. Informasi ini penting untuk orientasi petugas, bukan sekadar kosmetik profil. |
| UX-05 | Entry flow web untuk pengguna yang belum login terasa tidak langsung: root `/` mengarah ke dashboard, lalu middleware baru melempar ke `/login`. Halaman login sendiri belum memberi bantuan konteks untuk first-time admin, sehingga pengalaman awal terasa seperti "masuk ke area terlarang lalu dipantulkan". | Web | 2 | `apps/web/src/app/page.tsx` langsung `redirect('/dashboard/overview')`, lalu `apps/web/src/middleware.ts` memindahkan user tanpa token ke `/login`. `apps/web/src/app/(auth)/login/page.tsx` hanya memuat field login dan CTA tanpa bantuan `lupa password`, petunjuk kredensial, atau konteks peran. | Buat entry point tidak login yang lebih eksplisit: arahkan langsung ke login atau landing auth yang informatif. Tambahkan bantuan pemulihan akses dan microcopy yang menjelaskan siapa yang bisa masuk dan dengan kredensial apa. |
| UX-06 | Dashboard web untuk admin cenderung padat dan desktop-first. Banyak modul bernilai tinggi ditampilkan setara di sidebar, sementara layar CRUD utama seperti kelola kaleng menumpuk bulk action, primary action, search, dan beberapa filter dalam satu area. Ini efisien bagi power user, tetapi berat untuk admin baru atau pengguna browser HP. | Web | 3 | `apps/web/src/lib/menu-config.ts` menampilkan banyak menu utama pada level yang sama. `apps/web/src/app/dashboard/cans/page.tsx` merender bulk action, import, tambah data, search, dan filter status dalam satu header/toolbar. `apps/web/src/components/Sidebar.tsx` dan `apps/web/src/app/dashboard/layout.tsx` menunjukkan shell yang kuat untuk desktop dengan sidebar tetap. | Susun ulang IA berbasis journey: pisahkan aksi harian, monitoring, dan administrasi lanjutan. Gunakan progressive disclosure di toolbar, sederhanakan aksi default, dan audit ulang prioritas untuk browser HP lebar 360px. |

## 4. Perbandingan Konsistensi Web vs Native

| Area | Observasi | Dampak |
|---|---|---|
| Identitas visual | Web dan mobile sama-sama memakai nuansa hijau gelap, beige, dan aksen emas yang sejalan dengan palet "Earthy & Premium". | Fondasi branding sudah konsisten dan bisa dipertahankan saat redesign. |
| Model navigasi | Mobile mockup mengarah ke task-first flow (`Mulai Penjemputan`, `Scan`, `Riwayat`), sedangkan web lebih module-first dengan banyak menu administratif sejajar. | Prioritas tugas terasa berbeda antar platform; user lintas peran harus mempelajari dua mental model. |
| Prioritas aksi | Mobile mockup menonjolkan CTA primer besar, tetapi beberapa implementasi aktual mobile belum konsisten menurunkan ini ke layar detail tugas/riwayat. Web justru sering memunculkan banyak aksi sekaligus dalam satu viewport. | Hierarki aksi belum stabil lintas platform: mobile kurang tegas di beberapa layar aktual, web terlalu banyak aksi sekaligus. |
| Feedback operasional | Mobile sudah menempatkan status sinkronisasi sebagai bagian penting journey lapangan. Web memiliki modul audit/resubmit/WA monitor, tetapi status operasional tersebar ke halaman-halaman khusus. | Mobile lebih dekat ke kebutuhan real-time petugas; web berisiko terasa administratif dulu, operasional kemudian. |
| Kedalaman profil/konteks user | Web shell selalu menampilkan nama dan role di layout utama, sedangkan mobile profil masih dangkal walau backend menyediakan data lebih kaya. | Rasa orientasi identitas pengguna lebih kuat di web daripada di mobile. |

## 5. Rekomendasi Arah Redesign

1. Bangun ulang arsitektur informasi berbasis journey, bukan hanya berbasis modul.
   - Mobile: tugas -> scan -> koleksi -> riwayat harus terasa sebagai satu rangkaian.
   - Web: overview perlu menjadi pusat aksi harian, lalu modul administrasi menjadi layer kedua.
2. Perlakukan offline readiness sebagai fitur inti, bukan fallback.
   - Audit ulang semua titik yang masih memaksa internet untuk flow lapangan.
   - Tambahkan indikator kesiapan data offline dan recovery path yang lebih operasional.
3. Kurangi beban kognitif lewat penegasan aksi primer dan progressive disclosure.
   - Satu layar sebaiknya memiliki satu fokus utama.
   - Aksi sekunder/destruktif perlu disembunyikan sampai konteksnya tepat.
4. Standarkan pola affordance lintas platform.
   - Jika sebuah entitas adalah "tugas", maka aksi utama terhadap tugas harus serupa di mana pun user melihatnya.
   - Terminologi, state badge, dan pesan error perlu memakai bahasa yang sama antara web dan mobile.
